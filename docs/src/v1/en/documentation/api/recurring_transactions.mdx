# Recurring Transactions API

:::warning Beta
Recurring transactions are a beta feature. How monetr detects them and what the object looks like are both subject to
significant changes, so expect this page to move around a bunch before it settles down.
:::

Once monetr has grouped your transactions into [similar transaction](./similar_transactions) clusters, it looks at each
cluster and tries to work out whether it happens on a schedule. Your streaming service on the 12th every month, a
paycheck every other Friday, car insurance once a year. When it finds a schedule that holds up, that's a recurring
transaction.

A recurring transaction only ever goes one direction. Money going out and money coming in get looked at separately, so
a cluster can have at most two of them, one for the charges and one for the refunds or deposits. Most only ever have
one.

monetr wants at least three transactions before it'll call something recurring, and it has to be pretty sure about the
schedule. Two charges a month apart is a coincidence as far as it's concerned.

Like the clusters, this all happens in a background job. It runs right after the clusters get recalculated, so a brand
new transaction won't count toward anything until both jobs have gotten to it.

You can [list](#list-recurring-transactions) every recurring transaction on a bank account, or start from a
[transaction](./transactions#the-transaction-object), each one has a `transactionRecurringId` pointing at the recurring
transaction it's part of.

You can link a recurring transaction to the thing in your budget that covers it. A charge going out gets linked to an
[expense](./spending), money coming in gets linked to a [funding schedule](./funding_schedules), your paycheck for
example. The link lives on the recurring transaction, so you set it with a PATCH here after you've created the expense or
funding schedule.

## The recurring transaction object

| Attribute                | Type                    | Description                                                                                                                                                                                                       |
| ------------------------ | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `transactionRecurringId` | string (ulid)           | Identifies the recurring transaction. It stays the same between recalculations as long as the cluster keeps recurring in the same direction.                                                                      |
| `bankAccountId`          | string (ulid)           | The bank account it belongs to.                                                                                                                                                                                   |
| `transactionClusterId`   | string (ulid)           | The [similar transactions](./similar_transactions#the-similar-transaction-object) cluster it was found in.                                                                                                        |
| `transactionCluster`     | object                  | The [similar transactions](./similar_transactions#the-similar-transaction-object) cluster in `transactionClusterId`, without its `debug` info. Only there when listing, it's where the name comes from.           |
| `spendingId`             | string (ulid), nullable | The [expense](./spending#the-spending-object) tracking this, if you've linked one. Only ever set on debits. See [Link an expense or funding schedule](#link-an-expense-or-funding-schedule).                      |
| `spending`               | object                  | The [expense](./spending#the-spending-object) in `spendingId`, if there is one. Left out otherwise, and always left out when listing, look it up by `spendingId` instead.                                         |
| `fundingScheduleId`      | string (ulid), nullable | The [funding schedule](./funding_schedules#the-funding-schedule-object) tracking this, if you've linked one. Only ever set on credits.                                                                            |
| `fundingSchedule`        | object                  | The [funding schedule](./funding_schedules#the-funding-schedule-object) in `fundingScheduleId`, if there is one. Left out otherwise.                                                                              |
| `direction`              | string                  | `debit` for money leaving the account, `credit` for money coming in. Same as the sign on the transactions, debits are positive amounts and credits are negative.                                                  |
| `window`                 | string                  | Roughly how often it happens. One of `weekly`, `biweekly`, `firstAndFifteenth`, `fifteenthAndLast`, `monthly`, `bimonthly`, `quarterly` or `yearly`. `biweekly` is every two weeks, `bimonthly` every two months. |
| `ruleset`                | string                  | The actual schedule, as a [recurrence rule](./recurrence_rules). The days in it are your account's days, see the note below the table.                                                                            |
| `first`                  | timestamp               | The earliest transaction that's part of it. If something stopped for a long stretch and then started up again, this is from when it started back up.                                                              |
| `last`                   | timestamp               | The most recent transaction that's part of it.                                                                                                                                                                    |
| `next`                   | timestamp               | When monetr expects the next one, as of the last recalculation. Nothing updates it in between, so if the job hasn't run in a while this can already be in the past.                                               |
| `ended`                  | boolean                 | True once it's gone too long without a new transaction. monetr gives it half a period of slack past when the next one was due, and never less than 3 days, since charges like to wander around a bit.             |
| `confidence`             | number                  | How sure monetr is about the schedule, between 0.6 and 1. Anything under 0.6 doesn't get to be a recurring transaction at all.                                                                                    |
| `amounts`                | object                  | How many times each amount showed up. Keys are amounts in the currency's smallest unit, as strings since it's JSON, and values are counts. Handy for spotting a price change.                                     |
| `lastAmount`             | integer                 | The amount of the most recent transaction, in the currency's smallest unit. Usually your best guess for what the next one will be. See [Currencies](./currencies#how-monetr-stores-money).                        |
| `autoMatched`            | boolean                 | True when monetr linked the expense for you, because you kept spending its recent transactions from that expense. Goes back to false as soon as you change the link yourself.                                     |
| `createdAt`              | timestamp               | When monetr first decided it was recurring.                                                                                                                                                                       |
| `updatedAt`              | timestamp               | When it was last recalculated or linked. This changes on every recalculation, even when nothing about it did, so don't use it to spot changes.                                                                    |

The `ruleset` keeps its `DTSTART` in UTC like every other ruleset in monetr, but the schedule is really in your
account's timezone. If you want to pull dates out of it yourself, move `DTSTART` into your account's timezone first.
Skip that and something like `BYMONTHDAY=8` lands on the 9th for anyone east of UTC.

`ended` and deleted aren't the same thing. Something that ended still exists, it just isn't happening anymore. If a
cluster stops recurring entirely, or the cluster itself goes away, the recurring transaction gets deleted. Its ID stops
working and the transactions that were in it go back to a null `transactionRecurringId`. Whatever expense or funding
schedule was linked to it sticks around, it just isn't linked to anything anymore.

Recalculating doesn't touch the links. They stay put until you change them, or until you delete the expense or funding
schedule, which sets `spendingId` or `fundingScheduleId` back to null. The one exception is a debit with no links at
all: if two of its last three transactions were spent from the same expense, and nothing else is linked to that
expense yet, monetr links it for you and sets `autoMatched`.

## <Badge type="info">GET</Badge> List recurring transactions

Returns every recurring transaction on a bank account, a page at a time. Ones that are still going come first, sorted by
when the next one is expected, then the ones that have ended. You can narrow it down to one direction, or to just the
ones that are still going or just the ones that ended, so you're not paging through stuff you don't care about.

Each one comes with its `transactionCluster` so you have a name to show, but not its `spending`. If you need the expense
look it up by `spendingId`.

**In the app:** The recurring page, under transactions in the sidebar.

```http
GET /api/bank_accounts/:bankAccountId/recurring
```

**Auth:** API key, subscription required.

### Path parameters

| Attribute       | Type          | Required | Description                                             |
| --------------- | ------------- | -------- | ------------------------------------------------------- |
| `bankAccountId` | string (ulid) | Yes      | The bank account whose recurring transactions you want. |

### Query parameters

| Attribute   | Type    | Required | Description                                                                                                                                           |
| ----------- | ------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `limit`     | integer | No       | How many to return. Defaults to 25. Has to be between 1 and 100, or a 400.                                                                            |
| `offset`    | integer | No       | How many to skip first. Defaults to 0. Negative is a 400.                                                                                             |
| `direction` | string  | No       | `debit` or `credit`, to only get the ones going that way. Leave it off to get both. Anything else is a 400.                                           |
| `ended`     | boolean | No       | `false` for just the ones that are still going, `true` for just the ones that ended. Leave it off to get both. Has to be `true` or `false`, or a 400. |

### Example

```bash
curl --request GET \
  --url "https://my.monetr.local/api/bank_accounts/bac_01gds6eqsq7h5mgevwtmw3cyxb/recurring?direction=debit&ended=false&limit=1" \
  --user "$MONETR_API_KEY_ID:$MONETR_API_KEY_SECRET"
```

## <Badge type="info">GET</Badge> Get a recurring transaction

Returns one recurring transaction. You'll usually get the ID from a transaction's `transactionRecurringId`, or from
[listing them](#list-recurring-transactions).

**In the app:** The recurring card on a transaction's details page, and the recurring transaction's own details page.

```http
GET /api/bank_accounts/:bankAccountId/recurring/:transactionRecurringId
```

**Auth:** API key, subscription required.

### Path parameters

| Attribute                | Type          | Required | Description                                            |
| ------------------------ | ------------- | -------- | ------------------------------------------------------ |
| `bankAccountId`          | string (ulid) | Yes      | The bank account the recurring transaction belongs to. |
| `transactionRecurringId` | string (ulid) | Yes      | The recurring transaction you want.                    |

### Example

```bash
curl --request GET \
  --url "https://my.monetr.local/api/bank_accounts/bac_01gds6eqsq7h5mgevwtmw3cyxb/recurring/txrc_01j6b4n8w2kq5t9r3xm7vdc6ph" \
  --user "$MONETR_API_KEY_ID:$MONETR_API_KEY_SECRET"
```

```json

  "transactionRecurringId": "txrc_01j6b4n8w2kq5t9r3xm7vdc6ph",

  "fundingScheduleId": null,
```

### Errors

| Status | When                                                        |
| ------ | ----------------------------------------------------------- |
| 400    | Either ID is malformed.                                     |
| 404    | No recurring transaction with that ID on that bank account. |

## <Badge type="warning">PATCH</Badge> Link an expense or funding schedule

Links a recurring transaction to the expense or funding schedule that covers it, or clears that link. These are the
only two things you can change on a recurring transaction, everything else comes from monetr working it out.

A debit can only be linked to an expense, not a goal. A credit can only be linked to a funding schedule. For now an
expense or funding schedule can only be linked to one recurring transaction at a time.

**In the app:** Picking an expense or funding schedule on a recurring transaction's details page. Also creating one from
the recurring card on a transaction's details page or from the recurring page, the app creates it first and then links it
with this.

```http
PATCH /api/bank_accounts/:bankAccountId/recurring/:transactionRecurringId
```

**Auth:** API key, subscription required.

### Path parameters

| Attribute                | Type          | Required | Description                                            |
| ------------------------ | ------------- | -------- | ------------------------------------------------------ |
| `bankAccountId`          | string (ulid) | Yes      | The bank account the recurring transaction belongs to. |
| `transactionRecurringId` | string (ulid) | Yes      | The recurring transaction you're linking.              |

### Body

Send the one you're changing. Anything else in the body gets rejected.

| Attribute           | Type                    | Required | Description                                                                                  |
| ------------------- | ----------------------- | -------- | -------------------------------------------------------------------------------------------- |
| `fundingScheduleId` | string (ulid), nullable | No       | The funding schedule to link, on the same bank account. Credits only. Send null to clear it. |
| `spendingId`        | string (ulid), nullable | No       | The expense to link, on the same bank account. Debits only. Send null to clear it.           |

Sending a different ID just moves the link over, you don't have to clear it first.

### Example

```bash
curl --request PATCH \
  --url "https://my.monetr.local/api/bank_accounts/bac_01gds6eqsq7h5mgevwtmw3cyxb/recurring/txrc_01j6b4n8w2kq5t9r3xm7vdc6ph" \
  --user "$MONETR_API_KEY_ID:$MONETR_API_KEY_SECRET" \
  --header "Content-Type: application/json" \
  --data '{
    "spendingId": "spnd_01j6b5q2h8ycz4n7w3tkr9vx5d"
  }'
```

### Errors

| Status | When                                                                                                                                                                                                                                                                              |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | Either ID is malformed, the body has something other than `spendingId` or `fundingScheduleId`, you linked an expense to a credit or a funding schedule to a debit, you linked a goal, or that expense or funding schedule is already linked to a different recurring transaction. |
| 404    | No recurring transaction with that ID on that bank account, or the expense or funding schedule you sent doesn't exist on that bank account.                                                                                                                                       |
